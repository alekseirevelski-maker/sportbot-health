# Деплой бота sport-health

Сервер: Ubuntu VPS, `/opt/telegram-bots/sport-health`, systemd-сервис `sport-health`, Python 3.12.

## Правила

1. **Единственный путь деплоя — `deploy.sh`** в корне репозитория. Никаких ручных `git pull`, `scp`, копипаста кода.
2. **Правки на сервере запрещены.** Любой код попадает в прод только через коммит в git → тег → `deploy.sh`. Если на сервере найдены незакоммиченные изменения — это инцидент: зафиксировать, перенести в репозиторий, откатить сервер в чистое состояние.
3. **Релиз = тег** вида `vYYYYMMDD-N` (например `v20261106-1`, второй релиз за день — `v20261106-2`). Теги пушатся в origin: `git push origin vYYYYMMDD-N`.
4. **Откат = `bash deploy.sh <старый тег>`**. Откат — это тоже деплой, после него так же прогоняется смоук-чеклист и делается запись в журнал.
5. **На сервере не запускать «голый» `pytest` в корне репозитория.** До v20261112-1 в корне лежали файлы `test_*.py`, которые pytest собирал; `test_db.py` при импорте удалял данные прод-БД (инцидент 2026-11-11). Теперь `pytest.ini` ограничивает сбор каталогом `tests/`, деструктивный `test_db.py` удалён, но правило остаётся: тесты — только `python3 -m pytest tests/` или через `deploy.sh`.
6. **Одноразовые скрипты, которые пишут в прод-БД, не лежат в корне рабочей копии и не запускаются против прода.** С 18.11.2026 они сложены в `scripts/attic/` (git-игнор). Правка данных на проде — только отдельным разобранным скриптом: сначала копия БД (п. 7), затем dry-run, затем запись, и только по явному согласию владельца. След прежней ручной правки виден до сих пор: `data/sport_health.db.bak_bcdates_20261012_163950` — копия, снятая `_fix_bc_dates.py` перед изменением `record_date` прямо в `body_composition`.

7. **Копия прод-БД обязана существовать вне сервера.** Ночной бэкап лежит на том же диске (`backups/`, KEEP=10), поэтому при проблемах с диском или ошибочном удалении он бесполезен. Проверенная процедура (17.11.2026 19:24 UTC): `sqlite3 "file:data/sport_health.db?mode=ro" ".backup /tmp/stage.db"` → `gzip` → `scp` на другую машину → сверка `sha256` → `PRAGMA integrity_check` на восстановленном из gz файле.
## Деплой

```bash
ssh <server>
cd /opt/telegram-bots/sport-health
bash deploy.sh vYYYYMMDD-N       # релиз по тегу
bash deploy.sh                   # по умолчанию: ветка feature/cycle-auto-tracking
bash deploy.sh v20261020-1       # откат на старый тег
```

## Что делает deploy.sh (и как работает откат)

1. Запоминает текущую ревизию (`git rev-parse HEAD`) — точку отката.
2. `git fetch --tags origin`, затем `git checkout <ref>` и `git reset --hard origin/<ref>` (для ветки) или `git reset --hard <тег>` (для тега).
3. Если относительно предыдущей ревизии изменился `requirements.txt` — `pip install -r requirements.txt -q`.
4. Прогоняет тесты: `python3 -m pytest tests/ -x -q`.
5. Перезапускает сервис и до 30 секунд опрашивает `systemctl is-active sport-health`, затем показывает `tail healthcheck.log` и `journalctl -u sport-health`.

**Логика отката:** на любом из шагов 3–5 при ненулевом коде выхода скрипт делает `git reset --hard <точка отката>` + `systemctl restart sport-health` и завершается с кодом 1. То есть рабочее дерево и сервис возвращаются к состоянию, которое было до запуска деплоя. Откат идемпотентен: повторный запуск `bash deploy.sh <старый тег>` безопасен.

> Скрипт запускается через `bash deploy.sh …` — это работает независимо от исполняемого бита файла в git/чекауте (в репозитории он, тем не менее, закоммичен с режимом `100755`).

> Проверка синтаксиса скрипта: `bash -n deploy.sh`. Полный прогон логики отката выполняется на сервере в рамках задачи подготовки прода (Task 8 hardening-плана).

## Смоук-чеклист после деплоя

Прогоняется вручную после **каждого** деплоя/отката, результат — в журнал:

- [ ] **Меню врача:** раздел «🔔 На сегодня» присутствует; в списках видны **все** спортсмены.
- [ ] **Меню тренера:** тренер видит **только свои команды** (чужих спортсменов нет).
- [ ] **Анкета спортсмена с red-flag:** алерт приходит **и врачу, и тренеру** (два push-уведомления).
- [ ] **`/start` от заблокированного пользователя:** флаг блокировки сбрасывается, пользователь снова проходит регистрацию.
