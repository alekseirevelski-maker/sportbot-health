# Дизайн: харденинг и дашборд «Спортсмен ЧБК» (2026-11-05)

## Контекст и цель

Прод-бот мониторинга здоровья несовершеннолетних баскетболистов (systemd `sport-health`,
`/opt/telegram-bots/sport-health` на VPS mimobot 78.17.84.182; Python 3.12, PTB 22.8,
SQLite WAL). Канонический источник — этот репозиторий, ветка `feature/cycle-auto-tracking`
(md5 bot.py/database.py/config.py совпадает с продом на 2026-11-05). Бот активно
используется: 46 спортсменов, ~16–22 опроса в день.

Аудит 2026-11-05 нашёл: 4 критические дыры доступа (default-allow в диспетчере
callback'ов), права 777 на папку прода, бэкап `cp` без WAL, хрупкие рассылки,
блокирующий event loop, неподключённую валидацию. Владелец утвердил scope:
пункты 1, 2, 4, 5, 6, 7 из списка фич аудита + серверные фиксы (chmod, бэкап).

## Goals

1. **Default-deny контроль доступа к callback'ам** — закрыть `ban_/unban_/bc_team_/bc_overview_all`,
   добавить тренерский scope на `bc_view_/bc_import_to_`.
2. **Автоотписка заблокировавших бота** — флаг в БД, пропуск в рассылках, уведомление админу,
   блок на дашборде.
3. **Дашборд «🔔 На сегодня»** для врача/админа (все) и тренеров (свои команды).
4. **Деплой через git** — сервер тянет из GitHub, никаких `.bak`-копий как версиониования.
5. **Гигиена логов** — logrotate, убрать PHI (telegram_id, ФИО) из INFO-строк.
6. **Quick wins надёжности** — to_thread для тяжёлых точек, подключение validator.py,
   фикс напоминаний, lock на общее sqlite-соединение.
7. **Серверные фиксы** — chmod 750 на папку, бэкап через sqlite-снапшот (консистентный с WAL).

## Non-goals / anti-goals

- **Проверка согласий (consents) при выдаче данных — НЕ делаем** (решение владельца, 2026-11-05).
  Риск по 152-ФЗ остаётся принятым владельцем.
- Шифрование жалоб/консультаций at-rest — не в этом цикле (остаточный риск, кандидат на следующий).
- Рефакторинг bot.py на модули, миграция на ORM, замена SQLite — не трогаем.
- Поведение спортсменов не меняется: никаких новых полей в опросах.
- Anti-goal: сломать работающие рассылки/отчёты «улучшениями»; каждый шаг деплоится
  с проверкой healthcheck и откатом через git.

## Ограничения

- Прод живой, окно деплоя короткое (restart ~5–10 c, `Restart=always`); деплоить в
  малонагруженное время (не 03:00 UTC когда идут напоминания/бэкап, не утро когда сдача опросов).
- На сервере нет sqlite3 CLI — бэкап-снапшот делать через `python3 -c` (sqlite3 backup API).
- `.env` и `data/` никогда не попадают в git (уже в .gitignore — проверить, что не regress).
- Тесты (162) должны проходить локально без токена и прод-БД; новые фичи идут с тестами.
- GitHub-репо сейчас **публичное** — рекомендация владельцу: перевести в private до деплоя
  фичи 1 (callback-строки и логика доступа открыты). Решение владельца, не блокер кода.

## Решения владельца (дословно из разговора)

- Scope фич: «1 да 2 да 3 нет 4 да 5 да 6 да 7 да».
- Дашборд: врач утром видит «у кого какие алерты, на что важно обратить внимание».
- Тренеры видят дашборд **по своим командам** (scope как в отчётах).
- Тренеры **видят цикл-алерты** своих спортсменок («планируют нагрузку»).
- Серверные шаги и деплой **выполняет агент по SSH** (доступ есть); владелец
  подтверждает каждый деплой. Push в origin — агентом (проверить учётки до первого деплоя).
- Запись данных состава тела: **спортсмен — только свои** (существующий flow загрузки
  файла с весов, bot.py:429–475, сохраняется с `recorded_by=user_id`);
  `bc_import_to_<id>` (импорт чужому) — **только врач/админ** (`_is_full_access`).
- Тренер с дашборда открывает **полную карточку** спортсмена (включая расширенный
  состав тела), но только своих команд.

## Решения строителя (мои, владелец может поправить)

- **Пуш тренеру сразу после опроса (поправка владельца 2026-11-05):** тренер получает
  уведомление о красных флагах опроса спортсмена своей команды сразу после сдачи —
  тот же набор триггеров, что уходит врачу (handlers_survey.py:436–519: болезнь,
  обезболивающие, боль на игру, высокая боль NRS, пульс/HRV вне индивидуального
  коридора, критический Hooper), с фильтрацией по `coach_teams`. Рутинные опросы без
  отклонений тренеру НЕ пушатся (видны на дашборде). Вечерняя сводка, тренды и
  цикл-пуши — только `_full_access_ids()`, как сейчас.
- Ветка деплоя — текущая `feature/cycle-auto-tracking`, сервер трекает её; релизы тегами.
- dedicated-пользователь для сервиса (вместо root) — включён в серверные фиксы,
  но отдельным последним шагом с проверкой; если что-то мешает — остаётся root + chmod 750.
- Логика дашборда собирается из существующих запросов (`get_last_n_days_all`,
  `get_individual_baseline`, `cycle_alert_lines`, пороги `ALERT_THRESHOLDS`), тяжёлая
  сборка — через `asyncio.to_thread`.

## Фича 1. Default-deny гейт callback'ов

**Проблема:** диспетчер `callback_handler` (bot.py:1153) роутит ~80 веток без общего
гейта. Критичные незащищённые: `ban_<id>`, `unban_<id>` (bot.py:1301–1310),
`bc_team_<название>`, `bc_overview_all` (handlers_body_comp.py:88, 137).
`bc_view_<id>` (handlers_body_comp.py:260) проверяет роль, но не scope тренера;
`bc_import_to_<id>` (handlers_body_comp.py:939) — без проверки роли (запись данных
состава тела произвольному спортсмену).

**Решение:** центральная карта «префикс callback → требуемая роль» в одном месте
(новый модуль или таблица в bot.py): `admin_*`/`ban_`/`unban_`/`bc_*`-чтение-всех →
`_is_full_access`; `coach_*`/`bc_team_`/сводки → `_is_admin_or_coach` + scope.
Диспетчер перед роутингом сверяет префикс с картой; неизвестный префикс с
admin/doctor/bc-семантикой → отказ + лог. Точечные проверки внутри хендлеров остаются
(defense in depth). В `bc_view_<id>` добавить проверку scope тренера
(`athlete.team ∈ coach_teams`, переиспользовать `_scoped_athletes`-логику из
handlers_reports.py:37–41); врач/админ видит всех, тренер — полную карточку только
своих команд (решение владельца). `bc_import_to_<id>` — **только `_is_full_access`**
(импорт данных чужому спортсмену); спортсмен пишет свой состав тела через
существующий self-flow загрузки файла (bot.py:429–475), где athlete_id берётся из
его собственного профиля, а не из callback.

**Тесты:** unit-тесты карты (префикс → роль), тест «не-ролевой user_id получает отказ
на ban_/bc_overview_all», тест scope тренера на bc_view.

## Фича 2. Автоотписка заблокировавших

**Проблема:** 61 ошибка «bot was blocked by the user» в логе; напоминания ежедневно
долбятся в спортсменов #69/#91 (bot.py:1603 — только логирует).

**Решение:** колонка/флаг `bot_blocked INTEGER DEFAULT 0` в `athletes` (ad-hoc ALTER
в существующем механизме миграций database.py:230–369). В рассылках и напоминаниях:
`except telegram.error.Forbidden` → `db.set_bot_blocked(athlete_id, 1)`, пропуск.
Перед отправкой — skip заблокированных. Однократное уведомление `_full_access_ids()`:
«Спортсмен N заблокировал бота — мониторинг прерван». Разблокировка: флаг сбрасывается
при любом входящем апдейте от пользователя (`/start`). Заблокированные видны на дашборде
(блок «слепые зоны»).

**Тесты:** fake bot, кидающий Forbidden → флаг выставлен, второй прогон не шлёт, уведомление одно.

## Фича 4. Дашборд «🔔 На сегодня»

**Кто видит:** врач/админ (`_is_full_access`) — все спортсмены; тренер
(`is_coach`) — только свои команды (`coach_teams`). Пункт меню «🔔 На сегодня»
появляется у обеих ролей; у спортсмена — нет.

**Экран (один message, сверху вниз):**
1. 🔴 **Красные флаги сегодняшних опросов** (по строке: ФИО, команда, что именно):
   `illness_flag`, `analgesics`, `pain_on_game`, боль NRS высокая, жалобы (текст,
   обрезка), пульс покоя/HRV вне индивидуального коридора (`get_individual_baseline`,
   2 отклонения подряд — как в существующей логике алертов), Hooper ниже `ALERT_THRESHOLDS`
   (critical — в красный, warning — в жёлтый).
2. 🟡 **Тренды**: паттерны «3 дня подряд» (те же, что в `_check_trend_alerts`,
   но on-demand) + `cycle_alert_lines` (задержки/аменорея) — **тренерам показываются
   по их командам** (решение владельца).
3. ⚪ **Слепые зоны**: не сдали опрос сегодня; `bot_blocked=1`.
4. Inline-кнопка на каждой строке → **полная карточка спортсмена** (`bc_view`,
   включая расширенный состав тела) с единой проверкой scope: врач/админ — все,
   тренер — только свои команды (решение владельца 2026-11-05).

**Производительность:** сборка экрана — один `asyncio.to_thread`-вызов (batch-запросы,
не N+1); кэш результата на 60 с в памяти (два врача не собирают дважды).
Пустое состояние: «🟢 Тревог нет, N из M сдали опрос».

**Тесты:** сборка экрана на фикстурах БД (красный/жёлтый/слепые зоны), scope тренера
(своя команда видна, чужая нет), цикл-блок для тренера.

## Фича 5. Деплой через git

**Текущее:** на сервере ~30 файлов `bot.py.bak_*`, код правится по месту. Локальный
репо = прод (md5), origin есть, на origin только `main`, прод-ветка не запушена.

**Решение:**
1. Запушить `feature/cycle-auto-tracking` в origin; сервер: `/opt/telegram-bots/sport-health`
   становится git working tree (инициализация на месте: `git init` + remote + fetch +
   checkout ветки с сохранением `.env`, `data/`, логов — они в gitignore).
2. `deploy.sh` (в репо): `git pull` → `pip install -r requirements.txt` (если менялся) →
   `python3 -m pytest tests/ -x -q` (прогон на сервере до рестарта) → `systemctl restart
   sport-health` → tail healthcheck/журнала 30 с → при ошибке `git checkout <предыдущий
   tag>` + restart. Релиз = тег `vYYYYMMDD-N`.
3. Старые `.bak`-файлы и мусор (`bot_new.py`, `bot_orig.py`, `anketa.db`, `sport_health.db"`)
   — в архив `_bak_pre_git_<дата>.tar.gz` вне git, из папки удалить.
4. README: раздел «Деплой» (единственный путь — deploy.sh; правки на сервере запрещены).

## Фича 6. Гигиена логов

- **logrotate** на сервере: `/etc/logrotate.d/sport-health` для `bot.log`
  (weekly, rotate 4, copytruncate — процесс держит файл; healthcheck.log и backup.log тоже).
- **PHI из логов:** bot.py:1167 (callback + telegram_id на каждое нажатие) → уровень
  DEBUG или убрать id; bot.py:1796, handlers_admin.py:668,700, handlers_registration.py:23
  (ФИО + id) → только внутренний athlete_id без ФИО/telegram_id. Ошибки — с id, но без
  содержимого жалоб.
- Ротация существующего bot.log при деплое (logrotate -f).

## Фича 7. Quick wins надёжности

1. `asyncio.to_thread`: `generate_weekly_report` (bot.py:1767) и парсинг часов
   (bot.py:429 → watch_parser.py:269). Excel-отчёты handlers_reports.py — обернуть
   `wb.save` + тяжёлые выборки в `_db_run`/to_thread (минимально, без переписывания).
2. **Lock на sqlite-соединение**: `threading.Lock` вокруг execute/commit в database.py
   (общее соединение с check_same_thread=False используется из loop и executor — гонка).
3. **Validator**: `q_age` (bot.py:972) — диапазон из AGE_GROUPS вместо 10–99;
   `q_birth_date` (bot.py:990) — `parse_birth_date` (календарная валидация) +
   `validate_age_ge14`; `q_phone` (bot.py:980) — нормальный regex. Код validator.py
   уже написан и протестирован — подключить.
4. **Напоминания**: bot.py:1893 — сравнивать полное время, а не `hour>= and minute>=`;
   `reminder_sent_date` ставить ДО цикла рассылки (краш ≠ дубли после фикса Forbidden —
   дубль хуже пропуска? Нет: ставим до цикла, при крахе часть не получит — фиксируем
   в логе; выбор строителя: до цикла); 429 — пауза по `retry_after`.
5. `drop_pending_updates=True` (bot.py:1950) — не разгребать backlog после простоя
   (решение строителя: для reminder-бота старые апдейты бесполезны; владелец может поправить).

## Серверные фиксы (вне кода; выполняет агент по SSH, владелец подтверждает каждый шаг)

1. `chmod 750 /opt/telegram-bots/sport-health`, владелец файлов — будущий dedicated user или root.
2. `sport-health-backup.service`: вместо `cp` — снапшот через
   `python3 -c "import sqlite3; sqlite3.connect('file:...?mode=rw',uri=True).backup(sqlite3.connect(dest))"`
   (консистентно с WAL). Проверка: integrity_check снапшота в скрипте бэкапа.
3. Dedicated user `sportbot` для сервиса (`User=sportbot`, chown data/.env, `chmod 600 .env`) —
   последний шаг, после прогона тестов под ним.
4. Очистка диска: journal vacuum (`journalctl --vacuum-size=200M`), удалить syslog.1/btmp.1
   после проверки, .bak-архивы бэкапов старше 30 дней (таймер уже чистит — проверить).
5. `ENCRYPTION_KEY` остаётся в .env (используется шифрованием анкеты, database.py:1123 —
   в аудите была неточность: ключ используется для анкеты; жалобы — нет, это non-goal цикла).

## Порядок работ

1. Фича 1 + тесты (критичные дыры; репо публичное — до фикса не деплоим остальное).
2. Фича 7 (quick wins) + Фича 2 + тесты — один релиз.
3. Фича 4 (дашборд) + тесты — отдельный релиз.
4. Фича 5 (перевод сервера на git) — после первого успешного деплоя вручную.
5. Фича 6 + серверные фиксы — последним заходом.

Каждый деплой: pytest на сервере → restart → healthcheck → смоук в Telegram
(меню врача, меню тренера, опрос спортсмена) → запись в журнал деплоя.
