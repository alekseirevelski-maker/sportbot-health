# Дизайн: автоматический учёт менструального цикла (по модели Flow/Flo)

Дата: 2026-10-18 · Проект: sportbot-health (`C:\Users\egoro\sportbot-health`)
Статус: черновик на утверждении у владельца

## Intent и почему сейчас

Владелец видит в отчётах «большой разброс по дням цикла». Аудит проде
(17 девушек, 784 записи) показал причину: день цикла вводится шестью
корзинками-кнопками, в БД пишется середина корзинки {3,8,13,18,23,28}
(97,6% записей), «день 1» за всю историю зафиксирован один раз, длина
цикла у всех = 28 по умолчанию. Ни непрерывность, ни персональная длина
цикла (`update_cycle_length_from_history`) не работают, овуляционная фаза
недостижима (2 записи), прогноз следующих месячных невозможен в принципе.

Решение владельца: сделать как в трекерах класса Flow/Flo — **автоматически**.
Девушка фиксирует только событие «месячные начались»; день цикла, фаза,
прогнозы считаются машиной.

## Goals

1. Устранить разброс: день цикла — непрерывная производная от якоря
   (дата последнего «начались»), а не ежедневный ручной выбор.
2. Получать честные «дни 1» → заработать должно уже написанное
   обучение персональной длины цикла (медиана интервалов).
3. Сделать достижимыми овуляция (риск ПКС ×2-5) и сигнал «задержка»
   (RED-S-маркер, сейчас недоступен без событий).
4. Свести ежедневный вопрос о цикле к одному тапу.
5. Отчёты: рассчитанный день, фаза, прогноз даты следующих,
   флаг задержки — вместо каши из «Последних записей» — на всех поверхностях,
   где цикл уже присутствует (ежедневный отчёт врачу/владельцу, вывод
   тренерам, Excel-экспорт, экран «Мой цикл»).
   **Решение владельца (18.10): строку цикла видят врач, владелец и тренеры.**

## Non-goals

- Оплодородительные/фертильные функции (спорт, несовершеннолетние).
- Вопрос/событие «месячные закончились»: тип `'end'` зарезервирован в схеме,
  UX для него в v1 не строится (решение владельца 18.10).
- Интеграции с носимыми девайсами, базальная температура, тесты на овуляцию.
- Веб-дашборд, экспорт мобильников отдельно от существующих отчётов.
- Переписывание исторических записей daily_wellness (784 строки остаются как есть).

## Anti-goals (что будет провалом)

- Девушка хоть раз должна считать/вводить число, чтобы цикл «жил».
- Пропуск опроса ломает счётчик (двигать якорь при пропуске нельзя).
- В отчёте снова возможны несоседние скачки дня (13→28→3).
- Тренеры/мальчики получают хоть один новый вопрос.

## Функциональная модель

### Данные
- Таблица `cycle_events`: `id, athlete_id, event_date DATE, type TEXT
  ('start'|'end'|'anchor'), source TEXT ('survey_button'|'one_time'|'manual'),
  created_at`. Тип `anchor` — ответ одноразового вопроса.
- `athletes.last_period_start DATE NULL` — денормализованный кэш последнего
  'start'-события (для быстрой работы существующих запросов).
- `athletes.cycle_length_default` — остаётся: сначала prior 28 (или ручной),
  после ≥2 интервалов 'start'-событий обновляется медианой (существующая
  логика, переключённая на cycle_events вместо daily_wellness.cycle_day=1).

### Движок (новый чистый модуль `cycle_engine.py`, без БД-зависимостей)
- `current_cycle_day(last_period_start, today, cycle_length) -> int`
  = (today − start).days + 1 **без оборачивания**: счётчик идёт дальше L,
  пока не придёт событие 'start' (запрещён скачок 28→3 из anti-goals).
  День 1 наступает только от события, никогда от переноса через mod.
- `predicted_next_period(last_period_start, cycle_length, today) -> date`.
- `delay_days(today, predicted_next_period) -> int|None` (>0 → задержка).
- Статусы: обычный (фаза по `get_cycle_phase`), «задержка» (>7 дней от
  прогноза: фазовых рекомендаций по нагрузке нет, консерсивный режим +
  строка врачу), «аменорея >90 дней» (красный флаг RED-S, просьба
  отметить дату последних через шаг «Исправить»).
- `is_irregular` по тем же границам 21-35, что сейчас.
- Фаза — существующая `cycle_medicine.get_cycle_phase(day, length)`; при
  задержке > 7 дней фаза не «лютеиновая вечно», а отдельный статус «задержка».
- Пропуск опросов не двигает и не сбрасывает якорь. Событие 'start' задним
  числом (коррекция) пересчитывает всё от новой даты.
- Ручная корректировка дня принимает диапазон 1..L+30 (валидатор bot.py
  расширяется, иначе «задержка» невозможно ввести).

### Развязки одноразового вопроса (решения строителя)
- Кнопка «Пока не было» → статус pre-menarche: цикл не спрашивается вовсе
  (реальная ситуация юниорских команд).
- Кнопка «Нет данных» → якорь не сохраняется; шаг цикла в опросе
  пропускается и не напоминается до тех пор, пока девушка сама не ответит
  на одноразовый вопрос (он всплывает снова только при входе в цикл через
  «Мой цикл»). Опрос в целом сохраняется с NULL cycle_day — как сегодня.
- Окно ввода даты — до 90 дней назад (>60 — легально: это как раз целевая
  аудитория флага RED-S); >90 → статус «аменорея», вопрос переформулировать
  нечем, только коррекция.
- События ('start'/'anchor') пишутся в момент тапа, не в `_finish_survey`:
  тап «🩸 Да» до бросания опроса должен переякорить цикл (иначе «Да»
  теряет смысл при обрыве).

### Поток опроса (только gender == female)
1. **Одноразово**, если якоря нет: «🩸 Какого числа начались последние
   месячные?» — кнопки: Сегодня / Вчера / 2 дня назад / 3 дня назад /
   4-7 дней назад (одна кнопка «на прошлой неделе») / ✏️ Ввести дату (ДД.ММ,
   валидация: не дальше 90 дней, не в будущем) / «Пока не было» /
   «Нет данных» (развязки — см. секцию ниже).
   Сохраняется `anchor`-событие →
   сразу вычисляются день и фаза, показывается «Сегодня день N (фаза),
   следующие месячные ~дата» → жалобы.
2. **Ежедневно** (заменяет блок кнопок 1-5/6-10/…): одна клавиатура
   «📅 Сегодня день N · фаза · следующие ~дата. Месячные начались сегодня?
   [🩸 Да] / [Нет] / ✏️ Исправить день».
   - «Нет» → в daily_wellness пишется вычисленный день/фаза → жалобы.
   - «Да» → 'start'-событие на сегодня, день=1, цикл перезапускается → жалобы.
   - «✏️ Исправить день» → существующий ручной ввод числа (сохраняет daily
     значение как факт, но якорь не трогает; отдельная кнопка «исправить дату
     начала» ведёт к одноразовому вопросу).
3. Мальчики/тренеры: поток не меняется вообще.

### Отчёты (врач/владелец/тренер)
- Источник строки — вычисление от cycle_events на дату отчёта:
  «День N · 🌙 Лютеиновая · след. ~ДД.ММ · ⚠️ задержка X дн. · цикл L дн.
  (по истории)».
- Поверхности (по решению владельца «закрывать разброс везде, где цикл есть»):
  1. ежедневный отчёт врачу/владельцу — добавить строку цикла каждой девушке
     (сейчас её там нет вовсе);
  2. экран «Мой цикл» (`show_cycle_info`) — непрерывный ряд вместо
     «Последние записи» с корзинками;
  3. Excel/полный экспорт — stored cycle_day/cycle_phase пишутся вычисленным
     значением, колонки не меняются;
  4. тренерский вывод — та же строка без детализации фазовых текстов
     (только день/фаза/задержка), как решено владельцем.
- Задержка > 7 дней добавляется в существующий pipeline алертов врачу
  (`_check_trend_alerts`, новый паттерн) — активный сигнал, а не только
  пассивная строка. Тренеры алерт не получают, только строку отчёта.
- Порог задержки для ⚠️: 7 дней (константа движка; red_flags уже говорит
  «>35 дней — исключить аменорею»).

### Совместимость и миграция
- ALTER athletes ADD last_period_start; CREATE TABLE cycle_events — идемпотентно
  в `_create_tables()`, как принятый стиль этого файла.
- Старые daily_wellness.cycle_day не переписываются; в истории отчётов
  до появления якоря — как есть.
- `update_cycle_length_from_history`: интервалы берёт из cycle_events
  ('start'|'anchor'), правило медианы/окна 15-45д не меняется.
- `get_cycle_history`/`show_cycle_info` переключаются на вычисленные дни
  (для дат до первого якоря — stored значения).

## Приватность (заметка владельцу)
Хранение даты начала последней менструации 17 несовершеннолетних — тот же
класс данных, что уже хранящийся cycle_day; лежат в той же БД (chmod 600,
WAL). Новых внешних каналов нет. Никаких пушей «тебе пора» вне опроса —
только вопросы внутри уже ежедневного опроса.
Владелец явно решил (18.10): строку цикла с датой прогноза и задержкой
получают также тренеры. Риск-оценка принята владельцем; при пересмотре —
достаточно выключить поверхность №4 в секции Отчётов.

## Решения строителя (мои, не согласованные явно)
- Даты кнопок одноразового вопроса — относительно «сегодня», не абстрактный
  календарь: телефоны у девушек разные, кнопочный UX надёжнее парсинга.
- Парный формат дат для ручного ввода — ДД.ММ без года (год выводится из
  окна 60 дней).
- 'anchor' тоже участвует в длине цикла как первое 'start'-событие.
- Порог «задержка» 7 дней; фаза при задержке — отдельный статус, не фаза.
- Stored cycle_day/daily_wellness пишется вычисленным значением — отчёты,
  читающие таблицу напрямую (Excel-экспорт), не деградируют.
